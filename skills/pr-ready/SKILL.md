# PR Ready

## Inputs

- `[BRANCH]`: the branch to publish.
- `[BASE]`: the PR base branch; defaults to `main`.

Analyze the committed branch changes, prepare reviewable evidence and a PR description, then publish the PR. Invoking this workflow authorizes a normal push of the specified branch, uploading relevant screenshots to the repository's hosting provider or configured attachment service, and creating or updating its PR. Do not commit unrelated local changes, force-push, merge, or deploy.

## Workflow

1. **Resolve the repository and scope.** Read applicable `AGENTS.md` files, required documents, contribution standards, and PR templates. Identify the hosting provider, authenticated access, head repository/remote, and base repository/remote, including fork relationships. Resolve `[BRANCH]` and `[BASE]` to commit SHAs, compute their merge base, and inspect `git diff <merge-base> <branch-sha>`. Use CodeGraph first when indexed to understand affected code. Report missing or ambiguous inputs; do not silently replace `main` with another base. If the diff is empty, report that there is nothing to publish. Keep uncommitted changes out of the published scope.
2. **Understand the changes.** Identify the concrete problem, resulting behavior, affected workflows, material risks, and available validation evidence. Determine whether users see UI changes, including changed shared components, styles, assets, and rendered content. Trace their actual consumers rather than relying only on file extensions. Identify an existing open PR by head repository, branch, and base; reuse a matching PR rather than creating a duplicate. Preserve its description format and user-authored context.
3. **Capture UI evidence when applicable.** Locate the branch's checkout or an existing preview and confirm the application actually serves the committed revision being published. Use the installed `agent-browser` skill to capture representative affected screens and states, with relevant viewport sizes, test data, and captions. Store images in a task-specific temporary directory outside the repository. Use synthetic data and keep secrets or unrelated personal data out of captures. If starting services is necessary, use the repository's documented setup with isolated writable state and available ports; leave existing processes alone. If no matching preview or runnable checkout is available, prepare the remaining PR content and report the concrete capture blocker rather than using another revision or claiming screenshots exist.
4. **Compose the PR.** Use [pr-body](../pr-body/SKILL.md) in compose mode with the resolved branch/base, diff findings, existing body or required template, validation evidence, and screenshot captions. Write a title and body centered on the problem and resulting behavior. Add diagrams only when they materially help explain the changes, using supported syntax such as Mermaid where available. Include screenshots when captured. Store the exact multiline body in a temporary file or a structured tool argument; with `gh`, use `--body-file`. Do not claim unexecuted tests passed or hide known failures.
5. **Publish branch and attachments.** Verify the remote branch state and push the specified branch normally to the resolved head remote when needed. Stop on divergence instead of force-pushing or rewriting history. Upload screenshots using a supported hosting attachment mechanism or the repository's configured service, preserving repository visibility and access controls. Replace any temporary attachment placeholders with real URLs. Do not commit screenshots to the source tree merely to obtain URLs or invent unsupported upload commands. If the provider requires a PR before accepting attachments, create it as a draft using the prepared body, attach the images, and finalize the body before marking it ready. If publication or required UI evidence is blocked, preserve the prepared body and captures and report what remains; do not claim the PR is ready.
6. **Create or update and verify.** Create the PR with explicit head and base and the prepared title/body, ready for review by default unless repository instructions or the user require a draft. For an existing matching PR, update its description while preserving existing metadata and draft status unless a change was requested. Read the PR back and verify its URL, head commit, base, title, body, diagram formatting, and screenshot accessibility for the intended reviewers. If the branch changed during preparation, reassess the diff and refresh affected content and captures before claiming readiness. Avoid adding reviewers, sending messages, or modifying unrelated PR settings without instructions.
7. **Clean up.** Close task-owned browser sessions and stop services started for capture. Remove temporary body files and screenshots only after verifying successful publication and attachments. On failure, preserve useful prepared artifacts and report their locations for retry. Leave user-owned services, files, branches, and checkouts intact.

## Deliverable

Return the PR link, head/base branches, and a brief description of the published changes and visual evidence. State draft status, material validation limitations, or remaining publication blockers. If publication failed, give the prepared artifact locations and next required action instead of a success claim.
