# Plan Execution

## Inputs

- `[IMPLEMENTATION_PLAN]`: the implementation plan, supplied directly, in the conversation, or through a referenced document.
- `[BRANCH]`: the starting branch. Default to the conversation's checkout branch, or the main checkout's current branch when there is no separate conversation checkout.
- `[BASE]`: the comparison base; defaults to `main`.
- `[STACK]`: optional stack context to which this work belongs. Apply its documented dependencies, ordering, and conventions. Clarify its meaning only when it affects implementation or validation and cannot be resolved from the supplied context or repository.

Create a new implementation branch from `[BRANCH]`; call it `[WORK_BRANCH]` throughout this workflow. Preserve the starting branch and its checkout. This workflow includes staging and committing task-owned changes on `[WORK_BRANCH]` so the worktree can be removed without losing the implementation. Do not push, merge, publish, or deploy unless separately requested.

## Workflow

1. **Establish the scope.** Read the implementation plan, applicable `AGENTS.md` files, nested instructions governing affected paths, and the documents they require. Follow them throughout implementation, review, validation, and cleanup. Resolve the starting branch and base to commit SHAs; report missing or ambiguous refs instead of silently substituting a different base. Inspect existing worktrees and uncommitted changes. Use the committed starting branch as the source; do not copy, stash, or discard unrelated working-tree changes. If the plan depends on uncommitted work, clarify how to preserve and include it before proceeding. Extract acceptance criteria and dependencies, including any supplied stack context. Resolve blocking product decisions rather than inventing them.
2. **Create the workspace.** Choose a descriptive, unused `[WORK_BRANCH]` name and an unused worktree path outside the existing checkout. Create the new branch at the resolved `[BRANCH]` commit and attach it to the new worktree. An existing checkout of the starting branch is expected and remains untouched; the newly created work branch is the one checked out in the task worktree. Record names, paths, and SHAs. Respect repository naming and local resource limits. Do not delete or repurpose an existing branch or worktree on a name collision. Re-read applicable instructions in the new worktree and perform all implementation there.
3. **Implement the plan.** Trace affected workflows and reusable implementations before editing; use CodeGraph first when indexed. Implement the smallest coherent change that meets the agreed scope, following project architecture, DRY, and local rules. Include necessary migrations, documentation, and meaningful automated coverage. Avoid speculative abstractions, dependencies, or unrelated cleanup. Commit coherent task-owned changes on `[WORK_BRANCH]` before the branch-based review so the review sees the actual implementation, not an empty or outdated committed diff.
4. **Review and apply corrections.** Use [coding-review](../coding-review/SKILL.md) to review `[WORK_BRANCH]` against `[BASE]`, explicitly covering correctness, DRY, unnecessary complexity, and repository conventions. Reassess findings against actual requirements and consumers, apply substantiated corrections, and explain disagreements. Do not introduce abstractions solely to combine code with different semantics. Commit the corrections and verify that they resolve the findings without creating new defects. Keep inherited changes from the starting branch distinguishable from task changes, especially when `[STACK]` describes dependent branches.
5. **Run automated validation and fix failures.** Discover existing project commands and run all applicable validation layers for the affected scope: unit, integration, automated end-to-end, lint, type checking, and builds where available and relevant. Explain missing layers or execution blockers instead of inventing commands or claiming coverage. Run checks sequentially, one exact test file per invocation, Jest with `--runInBand`, and one application or library per typecheck command. Enumerate relevant files and invoke them separately rather than running a suite, directory, or multi-file glob. Respect the isolation and cleanup rules of [test-execution](../test-execution/SKILL.md) for checks requiring services. Diagnose failures and correct their root causes; change tests only when evidence shows a test defect or an intentional contract change. Do not weaken assertions or suppress errors merely to pass. Rerun failed checks and coverage affected by corrections until they pass or a concrete blocker prevents progress.
6. **Prepare the application test plan.** Commit the current implementation and use [test-plan](../test-plan/SKILL.md) with `[IMPLEMENTATION_PLAN]`, `[BRANCH]=[WORK_BRANCH]`, and the explicitly resolved `[BASE]`. Cover the acceptance criteria, relevant edge cases, and collateral regressions grounded in changed dependencies. Preserve its test IDs and expected results. Carry forward automated results already obtained, while keeping proposed tests distinguishable from executed checks.
7. **Execute and correct in isolation.** Use [test-execution](../test-execution/SKILL.md) with the generated `[TEST_PLAN]` and `[BRANCH]=[WORK_BRANCH]`. It must use this existing worktree without moving the branch. Start the complete required stack in an isolated runtime, allocate temporary alternative ports for collisions without stopping the process holding the port, and populate an isolated database. Execute the tests, using `agent-browser` and isolated database inspection when needed. Capture evidence, shut down the isolated stack, analyze results, correct failures, and repeat until all required tests pass. A blocked or unexecuted test is not a pass. Keep runtime configuration and writable state separate from other environments.
8. **Verify the final result and save it.** Inspect all changes from testing, apply the same review standards to new corrections, and rerun automated checks or application tests affected by those corrections. Ensure the required coverage applies to the final code. Commit all intended implementation and test corrections, inspect the final diff, and record the resulting HEAD. Preserve reports and useful evidence outside the disposable worktree. Do not commit credentials, temporary runtime overrides, or generated test data.
9. **Remove the task worktree.** Confirm that task-owned services, browser sessions, and temporary runtime resources have been cleaned up, all intended changes are committed, and the worktree contains no unpreserved tracked or untracked work. Remove only the worktree created in step 2 using normal Git worktree removal; never force removal to bypass unsaved changes. Keep `[WORK_BRANCH]` and its commits available for review. If execution is blocked, clean up the runtime and preserve recoverable work in commits before removing the worktree when possible; if removal would lose work or evidence, retain it and report the exact reason and path. Do not claim successful completion while required tests or fixes remain blocked.

## Deliverable

Report concisely:

- The starting branch, base, created implementation branch, final commit, and supplied stack context when relevant.
- What was implemented and any material deviations from the plan.
- Review findings resolved or rejected, with brief reasons for disagreements.
- Automated and application test results, remaining failures, blockers, and coverage limitations.
- Runtime cleanup and worktree removal status, plus any retained resources or evidence locations.

The implementation remains on `[WORK_BRANCH]` after worktree removal. Limit success claims to the agreed requirements and checks actually completed against the final code.
